# Контракт агентской части для бэкенда и фронтенда

Дата: 28 октября 2026. Документ описывает текущий Python-интерфейс. HTTP-бэкенд с обязательным аккаунтом, профили и Postgres реализованы; HTTP-контракт и запуск описаны в [BACKEND_DEPLOYMENT.md](BACKEND_DEPLOYMENT.md). Источник схем — `src/travel_agent/domain/models.py`, поведения — `src/travel_agent/service.py`. Офлайн-пример полного взаимодействия — `examples/integration.py`.

Агент принимает сообщение либо структурированное действие, возвращает ответ и состояние поездки. Перелёты, поезда, автобусы и отели выбираются независимо. Фронтенд показывает отдельные списки транспорта и проживания; бэкенд передаёт выбранные идентификаторы агенту и сохраняет его версию состояния.

## 1. Ответственность компонентов

| Компонент | Ответственность |
|---|---|
| Агент | Понимание запроса, уточнения, вызовы источников, проверка условий, независимые карточки, выбор компонентов, совместимость, общий итог, пояснения и саджесты. |
| Бэкенд | Проверенная личность пользователя, доступ к его сессиям, HTTP, доставка событий, повтор доставки, ограничения нагрузки, подключение постоянного хранилища. |
| Фронтенд | Сообщения и прогресс, отдельные списки транспорта/отелей, выбранные части, недостающие части, ввод пользователя и редактируемые саджесты. |

`user_id` — доверенный вход агента. Бэкенд получает его только из действующей сессии аккаунта, а не принимает произвольное значение из браузера. Без входа бизнес-маршруты возвращают `401` до запуска агента и обработки тела запроса. Начальная cookie и CSRF защищают вход, но не разрешают гостевую работу. Агент разделяет данные по `user_id`, но не выполняет вход пользователя. Пароли, токены провайдеров и секреты модели в пользовательские сообщения не передаются.

Агент хранит поездки, историю ходов и версии в Postgres при PostgreSQL URL либо SQLite для автономных проверок. `profile_loader(user_id)` загружает явно сохранённый профиль только при создании новой сессии. Его город служит значением по умолчанию, пожелания — мягким контекстом для модели; текущая поездка имеет приоритет. Профиль редактируется через `GET/PATCH /api/profile`, а не через доменное действие `update_preference`, сохранённое для совместимости.

## 2. Python-интерфейс

```python
service = AgentService(
    db_path="data/agent.sqlite",
    data_mode="live",          # либо replay
    checkout_mode="disabled", # либо demo
    gateway=model_gateway,
)
result = await service.run_turn(turn_input, on_event=event_sink)
snapshot = await service.get_session(verified_user_id, session_id)
service.close()
```

`run_turn` возвращает `TurnResult`, `get_session` — `SessionSnapshot`. Для отсутствующей пары пользователь/сессия `get_session` поднимает `KeyError`. Имена функций не являются HTTP-маршрутами. Реализованный HTTP-контракт описан в `BACKEND_DEPLOYMENT.md` и `AUTH.md`.

У одной сессии закреплены `data_mode` и `checkout_mode`. Смена этих режимов через другой экземпляр сервиса даёт `mode_conflict`; для смены создаётся новая сессия. Live-данные не заменяются архивом при сбое источника. Replay использует исторические записи и не проверяет текущие цены.

## 3. Вход `TurnInput`

| Поле | Значение |
|---|---|
| `schema_version` | Сейчас `1`. |
| `request_id` | Уникальный идентификатор одного действия; при повторе доставки тот же. |
| `user_id`, `session_id` | Проверенный пользователь и выбранная сессия поездки. |
| `expected_state_version` | Последняя полученная версия состояния; для новой сессии `0`. |
| `input` | Тип действия из таблицы ниже. |
| `payload` | Аргументы действия. |
| `now` | Время с часовым поясом, заданное приложением. |
| `timezone` | IANA-часовой пояс; по умолчанию `Europe/Moscow`. |

| `input` | `payload` | Результат |
|---|---|---|
| `message` | `{"text": "Хочу найти отель в Казани…"}` | Понимание запроса, уточнение, поиск, изменение поездки либо ответ на вопрос. |
| `select_component` | `{"component_id": "…", "options_version": 3}` | Выбор одной актуальной карточки. |
| `remove_component` | `{"product_type": "hotel"}` | Снятие выбранного компонента этого типа; остальные выбранные части сохраняются. |
| `select_option` | `{"option_id": "…", "options_version": 3}` | Совместимость с прежним выбором целого плана из `options`. |
| `undo` | `{}` | Возврат к предыдущему выбранному составу с повторной проверкой. |
| `reject_action` | `{}` | Сброс ожидающего подтверждения. |
| `confirm_action` | `action_id`, `plan_id`, `plan_version`, `payload_hash` из `pending_action` | Подтверждение конкретного демонстрационного действия. |
| `update_preference` | Пока не поддерживается | Не использовать в интерфейсе как работающую функцию. |

`remove_component` снимает выбор, **не удаляя продукт из требований поездки**. Например, после снятия отеля `request.products` по-прежнему содержит `hotel`, а в плане снова не хватает проживания. Для отказа от проживания как услуги пользователь отправляет сообщение «Отель не нужен, ищи только перелёт»; агент меняет состав запроса.

Бэкенд использует идентификаторы карточек. Номера «перелёт 1», «поезд 1», «отель 1» существуют только в текстовом диалоге и считаются отдельно внутри каждого вида продукта. Отправлять индекс позиции вместо `component_id` нельзя.

## 4. Запрос поездки

`SessionSnapshot.request` содержит исходный город, направление, даты выезда/возвращения, взрослых, возраст каждого ребёнка, бюджет и его область, ограничения, `products`, `event_date`, `event_start_at`.

- `products=["avia","hotel"]` — исходный состав по умолчанию.
- `products=["hotel"]` — только проживание; `products=["avia"]`, `["rail"]` либо `["bus"]` — только выбранный вид транспорта.
- `products=["avia","rail"]` — сравнение альтернатив дороги, не требование купить оба вида транспорта.
- При выборе транспорта в плане остаётся одна транспортная альтернатива: перелёт, поезд или автобус. Новый выбор заменяет ранее выбранный транспорт.
- `event_date` — дата мероприятия, если известна. `event_start_at` содержит часовой пояс. Это отдельные поля: дата концерта не становится автоматически датой выезда.
- `budget_minor` и цены RUB выражены целым числом копеек. Итог рассчитывает агент; фронтенд только форматирует сумму. Явно названная абсолютная сумма в рублях проверяется по исходному сообщению: «по 40 тысяч на человека» хранится как 4 000 000 копеек с `per_person`; число путешественников применяется ровно один раз.
- Необязательное `request.nightly_budget_minor` хранит явно заданный лимит за ночь для hotel-only. `budget_minor` вычисляется как ставка × число ночей и пересчитывается при изменении дат. По умолчанию лимит относится ко всему размещению (`budget_scope=trip`); `per_person` используется только при явном «на человека». Новый общий бюджет заменяет ставку за ночь. Без известных дат поиск не начинается и общий лимит не выдумывается.
- Обязательные `constraints.wheelchair_accessible`, `quiet_room`, `away_from_elevator` сохраняются явно. Без подтверждения конкретного тарифа их статус `unknown`, такие предложения не становятся доступными для выбора. `false` означает только явно отменённое пользователем требование; общие amenities/рейтинг не считаются подтверждением.


Обычное пользовательское сообщение — основной способ задания/изменения этих полей. Передача готового `TripRequest` отдельным публичным действием пока не предусмотрена.

## 5. Результат для интерфейса

| Поле | Как использовать |
|---|---|
| `request_id`, `session_id`, `state_version` | Связать ответ с действием и заменить локальную версию состояния. |
| `message`, `questions` | Показать ответ и текущий вопрос. Для обычной поездки агент делает одно необходимое уточнение за ход; при предварительном обсуждении поездки на концерт допустим компактный блок до трёх недостающих вопросов. |
| `response_kind` | `trip` — работа над поездкой; `chat` — обычная реплика без изменения маршрута, выбора или подтверждения. При `chat` не выводить анкету и подсказки поездки. |
| `transport_options` | Карточки `avia`, `rail` и/или `bus`, отдельный блок «Дорога». |
| `hotel_options` | Карточки `hotel`, отдельный блок «Проживание». |
| `selected_components` | Фактически выбранные части поездки, включая неполный набор. |
| `component_errors` | Ошибки по видам продукта; успешные карточки другого продукта сохраняются. |
| `current_plan` | Выбранный состав, известный итог, проверки и недостающие продукты. |
| `plan_diff` | Объяснимые изменения относительно прошлого выбранного состава. |
| `suggestions` | До трёх объектов `{id,label,text}`. Клик подставляет редактируемый текст; автоматической отправки/выбора нет. |
| `suggestions_version` | Версия политики подсказок; сейчас `6`. Устаревшие сохранённые подсказки не считать актуальными. |
| `options` | Прежние полные комбинации для совместимости; новые отдельные списки не выводить из этого поля. |
| `warnings`, `search_diagnostics`, `search_coverage`, `evidence` | Сведения для объяснений и диагностики. Не заменять ими пользовательское `message`. |
| `pending_action`, `demo_order` | Необязательный отдельный сценарий имитации оформления. |

Карточка содержит `component_id`, `options_version`, `product_type`, `title`, `price_minor`, `currency`, `conditions`, сведения о происхождении/времени данных и доступные времена поездки/проживания. Показанные условия относятся к конкретному тарифу. Отсутствующее поле не означает «включено», «бесплатно» или нулевую цену. Схемы поставщика и внутренние ссылки тарифа не нужно реконструировать на фронтенде.

По текущему решению карточки источников в пользовательском интерфейсе скрыты. Связь с доказательствами остаётся в данных для проверки.

Для погоды «сейчас» обычный интернет-поиск не подтверждает время метеонаблюдения. Агент сообщает, что не может надёжно подтвердить текущую погоду, не выдаёт точные текущие значения и сохраняет ссылки. Поле `fetched_at` обозначает время получения данных, а не время наблюдения. Это ограничение не отключает исследование прогнозов на день/сезон, визовых требований и других вопросов.

### Значение статусов

| `status` | Поведение интерфейса |
|---|---|
| `needs_input` | При `response_kind=trip` показать текущий вопрос из `questions`, если он есть. При `chat` достаточно самого ответа; отсутствие плана не означает, что нужно снова спрашивать направление. |
| `research_ready` | Найдена информация о событии/направлении; это ещё не подобранная поездка. |
| `options_ready` | Есть подходящие варианты для запрошенного состава. |
| `partial` | Часть задачи не закрыта или комплект несовместим. **Продолжать показывать непустые `transport_options` и `hotel_options`.** |
| `plan_ready` | Есть выбранный план, который может быть неполным. Проверить `current_plan.complete` и `missing_products`. |
| `needs_confirmation` | Отдельно показать состав и условия именно текущего демонстрационного действия. |
| `completed_demo` | Создан локальный демонстрационный заказ; не показывать реальную бронь или оплату. |
| `error` | Показать понятную ошибку, обработать код и актуальную версию. |

`in_progress` и `handoff_ready` входят в схему для совместимости. Сейчас прямой `run_turn` ожидает завершения, а handoff не реализован. Бэкенд может организовать собственную асинхронную доставку, не выдавая её за существующий агентский сценарий.

Сумма `current_plan.total_minor` относится только к выбранным компонентам. `complete=false` или непустой `missing_products` запрещают показывать эту сумму как цену собранной поездки. Неоценённые расходы остаются отдельными. При несовместимом выборе агент возвращает `partial`; интерфейс показывает реально сохранённые `selected_components`, а не оптимистично отмеченную карточку.

Выбор транспорта может изменить дату заселения после ночного переезда и обновить гостиничную выдачу. После каждого ответа заменить карточки и их версии из ответа целиком; старый `component_id`/`options_version` не переносить в новую выдачу.

## 6. Повторы, восстановление и ошибки

Один `request_id` относится к **точному** входу: `input`, `payload`, `expected_state_version`, `now` и прочим полям. При потере ответа повторить весь прежний `TurnInput`, не создавать новый `now` и не обновлять его версию. Завершённый точный повтор возвращает сохранённый результат даже с прежней версией.

Новое действие получает новый `request_id` и последнюю версию состояния. Не угадывать следующую версию по статусу: всегда брать возвращённый `state_version`, а при конфликте загрузить `get_session`. Некоторые обработанные ошибки являются завершёнными ходами.

| Код | Действие |
|---|---|
| `state_conflict` | Загрузить сессию, показать актуальные данные, затем отправить новое действие с новой версией. |
| `request_id_conflict` | Один идентификатор использован для разных входов; исправить повтор доставки. |
| `stale_options` | Заменить выдачу актуальной и запросить новый выбор. |
| `stale_confirmation` | Старое согласие не относится к текущему составу; показать новое подтверждение. |
| `mode_conflict` | Создать новую сессию для другого режима. |
| `timeout`, ошибки источников | Использовать `retryable` и объяснение; ошибка не равна пустой выдаче. |

При восстановлении: создать сервис с теми же хранилищем и режимами → вызвать `get_session` с проверенным `user_id` → восстановить запрос, отдельные списки, выбранный состав и `state_version`. История текущей поездки ограничена; постоянный профиль пользователя этим вызовом не создаётся.

Ходы одной сессии последовательно исполняются в текущем процессе; запись защищена проверкой версии и транзакцией. Это не распределённая очередь. Архитектура нескольких серверов/процессов и общее хранение — ответственность будущей интеграции.

## 7. События прогресса

`on_event` принимает словарь с `event_id`, `run_id`, `sequence`, `timestamp`, `type`, `payload`. Используются `stage_changed`, `skill_loaded`, `tool_started`, `tool_finished`, `options_updated`, `confirmation_required`, `completed`. `run_id` связывает события с `request_id`, `sequence` упорядочивает их внутри хода.

Получатель должен быстро передавать событие в свою очередь доставки. Ошибка получателя не должна отменять доменные операции. Событие — сигнал прогресса; окончательным результатом остаётся возвращённый и сохранённый `TurnResult`. `timestamp` фиксирует время события, `elapsed_ms` — время от начала текущего хода по монотонным часам. Разница соседних событий помогает находить задержки, но не заменяет отдельные метрики параллельных операций.

## 8. Необязательное демонстрационное оформление

Для обычного подбора использовать `checkout_mode="disabled"`. Для отдельного демосценария при создании сессии выбрать `demo`:

1. Собрать полный совместимый план.
2. Отправить сообщение «Оформить».
3. Показать полученные состав, сумму, условия и явную пометку имитации.
4. После согласия отправить `confirm_action` с четырьмя полями из **текущего** `pending_action`.
5. Показать `completed_demo` как локальную симуляцию.

Изменение тарифа может потребовать нового подтверждения. `pending_action.expires_at` — срок действия внутреннего согласия, а не гарантия цены. Выбор карточки и нажатие саджеста не подтверждают заказ.

## 9. Проверяемый пример

```sh
uv run python examples/integration.py
uv run python examples/integration.py --demo-order
```

Пример использует временную SQLite-базу, rules и архив Москва — Ереван 24 ноября — 1 декабря 2026. Он проверяет точный повтор хода, отдельный выбор перелёта, восстановление, выбор отеля, вопрос об условиях, снятие и повторный выбор отеля. Флаг добавляет явно запрошенную локальную имитацию заказа. Рабочие пользовательские поездки не затрагиваются.

Успешный запуск примера подтверждает интеграционный контракт на архивных данных. Он не подтверждает качество настоящей модели, актуальность цен или работу живых источников. Проверки этих режимов фиксируются отдельно в `VERIFICATION.md`.

## 10. Рекомендации главного экрана

Рекомендации формируются отдельно от `TurnResult` и поиска предложений. Реализация: `src/travel_agent/recommendations.py` — каталог, извлечение интересов и ранжирование; `src/travel_agent/home_recommendations.py` — постоянное хранилище, статистика и восстановление истории. Поддерживаются SQLite и Postgres.

### HTTP и карточки

`GET /api/recommendations` требует действующую сессию аккаунта и возвращает объект:

| Поле | Тип и смысл |
|---|---|
| `personalized` | Массив до четырёх персональных карточек, с объяснением исходного интереса. |
| `popular` | Массив до шести популярных карточек либо редакционных стартовых идей. |
| `popular_source` | `community` — есть подходящая общая статистика; `starter` — использован стартовый каталог. |
| `history_used` | `boolean`: есть распознанные интересы текущего аккаунта в учитываемом окне. Не гарантирует непустой `personalized`, например после скрытия всех кандидатов. |

Форма одной карточки:

| Поле | Тип и смысл |
|---|---|
| `id` | Стабильный идентификатор темы, например `destination:korea` или `artist:imagine-dragons`; одинаковый во всех блоках. |
| `title`, `description`, `reason` | Строки для названия, описания и объяснения рекомендации. |
| `prompt` | Готовый редактируемый черновик нового сообщения. Клик по карточке не отправляет запрос автоматически. |
| `kind` | `destination`, `artist` или `theme`. |
| `source` | `personalized`, `popular` или `starter`. |
| `budget_minor` | `number` или `null`: бюджет пользователя в копейках, если применим общий или персональный лимит. Не является стоимостью предложения. Для бюджета за ночь используется `budget_label`, а это поле равно `null`. |
| `budget_label` | `string` или `null`: готовое пояснение с суммой и областью бюджета, включая «на человека», «на всех» или «за ночь». Показывать его целиком, не вычисляя область из суммы. |

`POST /api/recommendations/{id}/dismiss` скрывает тему для текущего аккаунта и возвращает `{"ok": true}`. Тело запроса не требуется. Нужны действующая сессия и заголовок `X-Travel-Token`; без входа — `401`, без корректного CSRF — `403`. Идентификатор допускает 1–100 символов `[A-Za-z0-9_:-]`; при построении URL следует использовать `encodeURIComponent`. Повторное скрытие безопасно. Скрытие сохраняется между устройствами и перезапусками, исключает тему из обоих блоков и не истекает вместе с 90-дневным окном. Обратный маршрут восстановления скрытой карточки пока не реализован. Ответы API имеют `Cache-Control: no-store`.

### Источники, ранжирование и ограничения

Сигналы создаются из завершённых сообщений зарегистрированного пользователя с сохранённой доменной квитанцией. Ответы `chat`, ошибки, действия выбора карточек и гостевая история до переноса в аккаунт не участвуют. Сохраняются канонический идентификатор темы, время и собственные условия поездки; необработанный текст запроса не копируется в таблицы рекомендаций. Бюджет и область бюджета, взрослые и возраст детей, длительность, город отправления и `products` передаются в черновик как условия подбора. Новые даты уточняются, цены и будущие концерты должны проверяться поиском. Рекомендация не означает подтверждённую доступность или возможность уложиться в прежний бюджет.

Учитываются сигналы за последние 90 дней включительно; персональное ранжирование читает максимум 500 последних строк текущего аккаунта. Для общего рейтинга берётся один последний голос на пару аккаунт/тема; нужны минимум три разных аккаунта. Вес голоса — `1.0` за последние 7 дней, `0.7` за последние 30 дней и `0.4` за оставшуюся часть окна. В общую выдачу передаются только тема и агрегаты, без исходных сообщений, идентификаторов пользователей и личных условий поездки. При отсутствии подходящих популярных тем выдаются стартовые идеи, которые не обозначаются как реальная популярность.

Каталог связей редакционный и ограниченный: распознаются только направления, исполнители и темы, перечисленные в `CATALOG`. Неизвестный запрос остаётся обычным запросом агента, но сам по себе не расширяет каталог рекомендаций. Для расширения нужно добавить тему, варианты написания и обоснованные связанные интересы; каталог не содержит расписаний концертов и тарифов.

### Постоянное хранение и восстановление

- `recommendation_signals`: `user_id`, `session_id`, `request_id`, `topic_id`, UTC-время `occurred_at`, JSON `context`. Первичный ключ `(user_id, session_id, request_id, topic_id)` не допускает двойного учёта при повторной доставке.
- `recommendation_processed_jobs`: отметки обработки с ключом `(user_id, job_id)`. Отметка записывается после сигналов; прерванная обработка безопасно повторяется. Отметки сохраняются и после истечения сигналов, поэтому старые запросы не восстанавливают уже истёкшие интересы.
- `recommendation_dismissals`: `(user_id, recommendation_id)` и `dismissed_at`. Повторное скрытие обновляет время, не создавая дополнительную запись.

Завершение нового HTTP-запроса сразу обновляет сигналы. При чтении ленты выполняется ограниченное восстановление пропущенной или прежней истории: до 100 необработанных завершённых запросов владельца и ещё до 300 по всем зарегистрированным аккаунтам. Большая прежняя история обрабатывается за несколько чтений. Текущие параметры сессии применяются к старому сообщению только при совпадении версии состояния с его результатом; иначе интерес извлекается из явного текста, чтобы не приписать ему более поздний бюджет или направление. Очистка сигналов старше 90 дней происходит при чтении ленты; исходные поездки и переписка остаются в своих таблицах.
