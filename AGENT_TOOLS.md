# Агент путешествий: модель и инструменты

Дата проверки: 27 октября 2026. Контракты ниже — проект нашего пакета. Схемы Туту взяты из сохранённого tools/list от 26 октября; перед подключением их нужно сверить с работающим сервером.

Основная спецификация: [AGENT_SPEC.md](AGENT_SPEC.md). Порядок реализации: [AGENT_IMPLEMENTATION_PLAN.md](AGENT_IMPLEMENTATION_PLAN.md).

## 1. Hugging Face

Выбран доступ к модели через Hugging Face Inference Providers. Это не фиксирует конкретную модель, вычислительного провайдера или стоимость. Модель должна отвечать по-русски и устойчиво проходить цепочку вызова инструмента.

Основной путь: LangGraph → ModelGateway → ChatHuggingFace + HuggingFaceEndpoint → HF Inference Providers. У LangChain есть официальный пакет langchain-huggingface и документированный способ подключения этих классов. [Интеграция Hugging Face](https://docs.langchain.com/oss/python/integrations/chat/huggingface).

ModelGateway скрывает от графа конкретный способ подключения. Его вход — сообщения и схемы разрешённых функций; выход — текст и/или типизированные запросы на вызов. Исполняет функции приложение.

### Конфигурация

Это образец будущего .env.example, не уже работающая конфигурация:

~~~dotenv
HF_TOKEN=
HF_MODEL_ID=
HF_INFERENCE_PROVIDER=

TUTU_MCP_URL=https://mcp.tutu.ru/mcp
AGENT_DATA_MODE=live
AGENT_CHECKOUT_MODE=demo
AGENT_DEFAULT_CURRENCY=RUB
AGENT_DEFAULT_TIMEZONE=Europe/Moscow

AGENT_STATE_DB=./data/agent.sqlite
AGENT_CHECKPOINT_DB=./data/checkpoints.sqlite
AGENT_MAX_TOOL_ROUNDS=6
AGENT_MAX_EXTERNAL_CALLS=20
AGENT_TOOL_CONCURRENCY=3
AGENT_TURN_TIMEOUT_SECONDS=90
AGENT_TOOL_TIMEOUT_SECONDS=20
~~~

HF_MODEL_ID — модель на Hub; HF_INFERENCE_PROVIDER — сервис, который её исполняет. auto выбирает провайдера, а не модель. Для воспроизводимости сначала закрепляем проверенную пару; автоматическую маршрутизацию можно включать отдельно. [HF Inference Providers](https://huggingface.co/docs/inference-providers/en/index).

В приложении используем одно имя секрета HF_TOKEN. При создании LangChain-интеграции явно передаём его в поддерживаемый параметр или сопоставляем с HUGGINGFACEHUB_API_TOKEN. Нужен токен с разрешением Inference Providers; доступ, лимиты и баланс проверяются перед живым запуском. [HF Chat Completion](https://huggingface.co/docs/inference-providers/en/tasks/chat-completion).

### Проверка совместимости перед разработкой графа

Для конкретной пары model/provider выполнить:

1. Короткий ответ по-русски.
2. Вызов безопасной локальной функции с двумя типизированными аргументами.
3. Возврат результата по правильному tool_call_id.
4. Итоговый ответ, использующий результат функции.
5. Обработку ошибки инструмента без выдуманного успеха.
6. Разбор запроса поездки в нашу схему с проверкой Pydantic.
7. При необходимости — потоковую выдачу; отсутствие streaming не блокирует первый рабочий запуск.

Поддержка tools, строгой JSON-схемы и streaming зависит от модели и провайдера. Наличие интеграции не гарантирует эти возможности любой модели на Hub. Если strict недоступен, остаются проверка схемы кодом и ограниченное исправление ответа; не выполняем строковый код, сгенерированный моделью. [HF Function Calling](https://huggingface.co/docs/inference-providers/en/guides/function-calling).

Если проблема в LangChain-обёртке, запасной ModelGateway можно сделать поверх AsyncOpenAI с base_url=https://router.huggingface.co/v1 и HF_TOKEN. Для явно выбранного провайдера model имеет формат MODEL_ID:PROVIDER; при HF_INFERENCE_PROVIDER=auto передаём MODEL_ID без суффикса. Суффикс :auto не конструируем. Запрос идёт в HF; сохранение связей tools/tool_calls/tool_call_id остаётся обязательным. [Совместимый API HF](https://huggingface.co/docs/inference-providers/en/tasks/chat-completion). Этот вариант не исправляет отсутствие tool calling у самой пары model/provider.

Модель в этих документах не выбрана и живым запросом не протестирована. Назначать конкретный ID без такой проверки не следует.

## 2. Подключение Туту MCP

Адрес: [https://mcp.tutu.ru/mcp](https://mcp.tutu.ru/mcp). При проверке 26 октября сервер был доступен без авторизации. Это наблюдение, а не обещание бессрочного доступа, SLA или отсутствия лимитов.

По актуальной документации LangChain подключение MCP выполняется через langchain.mcp.MCPAdapter и extra langchain[mcp] версии не ниже 1.4.0. API обозначен beta; зависимости следует зафиксировать после проверки. HTTP URL использует Streamable HTTP. [Документация MCP](https://docs.langchain.com/oss/python/langchain/mcp), [миграция со старых адаптеров](https://docs.langchain.com/oss/python/migrate/langchain-mcp-adapters).

При старте адаптер:

1. Подключается и читает tools/list.
2. Проверяет наличие необходимых инструментов и ожидаемые поля схем.
3. Сверяет их с нашей разрешённой конфигурацией.
4. Загружает инструкции только нужных продуктов.
5. Публикует capabilities для графа.
6. При несовместимости сообщает schema_changed/capability_unavailable; не угадывает новый формат.

Ни аннотация readOnlyHint, ни текст описания сами по себе не дают инструменту разрешение. Политика определяется нашей проверенной allowlist. Схемы и ответы внешнего сервера не могут заменить правила агента.

## 2.1. Локальные инструменты skills

Эти функции реализуем внутри приложения; в MCP Туту их нет:

- load_skill(name) — получает зарегистрированное имя и возвращает body, version/hash и список доступных reference_id;
- read_skill_reference(skill_name, reference_id) — возвращает выбранный справочный материал этого навыка.

Имена выбираются из SkillRegistry, ссылки — из ресурсов активированного навыка. Прямой произвольный путь или URL не принимается. Загрузчик проверяет принадлежность файлов каталогу навыка, включая разрешение символьных ссылок.

На старте проверяются YAML-поля name/description, уникальность имён и существование нужных ресурсов. Каталог ресурсов поставляется вместе с Python-пакетом; он доступен и после установки, независимо от текущей рабочей папки.

В route модель выбирает применимые навыки по каталогу; load_skills загружает инструкции до соответствующих действий. Повторная активация той же версии не дублирует текст в контексте. После смены задачи набор активных инструкций пересматривается.

Разрешённые бизнес-инструменты определяются кодом, возможностями адаптера и режимом исполнения. Рекомендации из навыка могут сузить выбор, но не добавить полномочия. Общие проверки стоимости, state_version, pending_action и data_origin действуют при любом навыке.

## 3. Какие инструменты доступны

Источник списка — [сохранённый tools/list](exports/tutu-yerevan-2026-10-26/tools_list.json). В нём 17 инструментов.

| Возможность | Инструменты | Политика нашего агента |
|---|---|---|
| Отели | search_hotels, get_hotels_instructions | Разрешить чтение |
| Авиа | search_avia, get_avia_instructions | Разрешить чтение |
| Поезда | search_rail, get_rail_instructions, get_rail_seatmap | Разрешить чтение |
| Детали | get_offer_details | Разрешить чтение с проверкой product_type и ссылок |
| Ресурсы | fetch_resource | Только ссылки ресурсов, полученные от настроенного сервера |
| Другой транспорт | search_bus, search_etrain, search_multitransport и три соответствующих get_*_instructions | Подключать по capability; не обязательны для первого сквозного сценария |
| Ссылка на оформление | create_checkout_link | Только в явно включённом handoff-режиме |
| Регистрация пассажиров | register_checkout_passengers | Исключить из разрешённых инструментов этой реализации |

В сохранённой схеме create_checkout_link помечен readOnlyHint=true, idempotentHint=true. Он формирует ссылку; это не подтверждение покупки. register_checkout_passengers помечен readOnlyHint=false, idempotentHint=false и может иметь реальные последствия для заказа/удержания мест. Он не используется для имитации.

В базовом графе модели не показываются все инструменты сразу. Набор ограничивается текущим продуктом и задачей. Транспортные инструкции запрашиваются один раз на версию схемы и обновляются при её изменении.

## 4. Наш контракт адаптера

Это внутренние методы, а не названия готовых MCP-инструментов:

~~~python
class TravelToolsAdapter:
    async def capabilities(self) -> Capabilities: ...
    async def search(self, query: SearchQuery) -> SearchPage: ...
    async def details(self, ref: OfferRef, scope: DetailScope) -> OfferSnapshot: ...
    async def seat_groups(self, ref: OfferRef, request: SeatGroupRequest) -> SeatGroupResult: ...
    async def refresh(self, selected: SelectedComponent) -> RefreshResult: ...
    async def checkout_link(self, selected: SelectedComponent) -> HandoffResult: ...
~~~

SearchPage: offers, coverage, next_page, has_more, fetched_at, data_origin, warnings, error.

Coverage: provider, product, нормализованный запрос, прочитанные страницы, количество уникальных предложений, total если дан поставщиком, total_exact, complete, stop_reason. Динамическая пагинация может менять выдачу; даже прочитанные страницы не гарантируют глобального минимума.

RefreshResult: status = unchanged / changed / unavailable / unknown; новый снимок, изменения и доказательства. Это не блокировка цены.

Сохраняем ссылку на исходный ответ и соответствие нормализованного поля исходному пути. В граф передаём только нужный фрагмент; полная запись используется для расследования и регрессионной проверки.

Нормализованный результат ошибки: code, retryable, provider, operation, message, evidence_ref. Коды: timeout, rate_limited, unavailable, invalid_arguments, schema_changed, unsupported, stale_offer, fixture_missing. Корректная пустая выдача — успешный ответ с пустыми offers.

## 5. Отели: обязательные особенности

Поиск: search_hotels с city_name/geo_id, check_in, check_out, adults и children_ages. Названия параметров берутся из схемы, не из иллюстративных статей.

Детали: get_offer_details с product_type="hotels" — именно множественное число в проверенной схеме — и возвращённым hotel_id/hotel_geo_id, датами и гостями. Наш внутренний тип hotel адаптер переводит в этот внешний enum.

- best_offer.price в поиске — стоимость всего проживания для запрошенного состава гостей.
- price_max в фильтре поиска задаётся за ночь. Нельзя передать туда общий бюджет всей поездки.
- Для выбора нужен конкретный номер и тариф, а не только отель и его минимальная цена.
- hotel_id/hotel_geo_id, tutu_offer_id и идентификаторы тарифов имеют разный смысл; они не взаимозаменяемы.
- Имена offerpack_hash и offer_pack_hash могут отличаться между ответом и аргументами оформления. Нужен явный маппинг по схеме; нельзя конструировать значение.
- view="rules" нужен для полной лестницы отмены; compact оставляет сокращённые сведения.
- Бесплатная отмена имеет дедлайн, часовой пояс и последующие штрафы. «Можно вернуть» не означает «можно вернуть бесплатно».
- Отсутствующие площадь, тип кровати, вместимость или собственная ванная остаются неизвестными.
- Для цитирования отзывов нужен view="reviews"; агрегатная ИИ-сводка не считается отзывом гостя.

Факт из сохранённого примера: Median имел 32 320 ₽ в листинге и 32 702 ₽ в подробном тарифе. Для выбранного плана применяется подробный выбранный тариф, а изменение суммы явно отражается. Это исторический пример, не текущая цена.

## 6. Авиа: обязательные особенности

Поиск: search_avia с origin, destination, departure_date, при необходимости return_date, составом пассажиров и фильтрами.

- price относится ко всей запрошенной группе. Повторно умножать на число взрослых нельзя.
- Проверяется конкретный variants[]: багаж, ручная кладь, возврат, обмен и класс.
- Базовая цена карточки может отличаться от цены выбранного тарифного варианта.
- Перелёт туда-обратно не складывается повторно по сегментам, если цена уже общая.
- Локальное время отправления/прибытия сохраняется вместе с часовым поясом.
- get_offer_details для avia в сохранённой схеме может просто переформатировать переданный compact offer. Это не обновление цены или наличия.

Поэтому refresh для авиапредложения повторяет подходящий поиск, сверяет маршрут, сегменты и тариф. Если точно сопоставить предложение нельзя, возвращает unknown или новую явно обозначенную альтернативу. Нельзя выдать похожий рейс за подтверждение прежнего тарифа.

Инструмента схемы мест самолёта в проверенном наборе нет. Умение проверять железнодорожные места не переносится автоматически на авиа.

## 7. Поезда и места вместе

Последовательность:

~~~text
search_rail(...)
→ выбрать предложение
→ взять offer.details_ref без изменений
→ get_rail_seatmap(details_ref=..., task="together", seats_together=4)
→ проверить группу мест и её ограничения
~~~

seats_together поддерживает 2–6 человек. Можно ограничить запрос car_number. Другие задачи: summary, far_from_wc, female. Для целевой задачи обычно достаточно компактного ответа.

Проверить для каждой группы:

- один нужный вагон и соответствующая секция/купе;
- номера мест и их доступность по данным ответа;
- типы полок, этаж и основные/боковые места;
- категорию вагона и реальную вместимость;
- ограничения пола и класса обслуживания, если переданы;
- общий совместимый тариф и его применимость к группе.

total_price группы в описании инструмента — предварительный взрослый итог с общим тарифом. Это не гарантированная итоговая корзина и не расчёт детских скидок. Поисковая цена за место также не доказывает стоимость конкретной семейной группы.

Если группы нужного размера нет, использовать largest_group_available и меньшие группы как альтернативы, явно описывая разделение. Нельзя объявить разрозненные места соседними. no_layout_for_carrier означает отсутствие возможности проверки, а не отсутствие мест.

В предыдущей живой проверке встречалась противоречивая группа LUX/СВ на четыре места при описании двухместного купе. Это отдельный регрессионный сценарий: такие данные требуют проверки и не подтверждают «одно купе».

Сидячие места одной секции не обязательно находятся без прохода между ними. Координаты схемы и расстояние до туалета в пикселях не являются расстоянием в метрах.

## 8. Повторная проверка и ограничение поиска

Для нового выбора обновляются детали нужного тарифа; перед оформлением проверяются именно выбранные компоненты. После изменения дат, гостей или ограничений поиск выполняется заново для затронутых компонентов.

Сохранённый offer_id или hash — непрозрачная ссылка, а не гарантия наличия. Если поставщик изменил ID, сравнение по маршруту/тарифу должно вернуть новый снимок и показать изменение.

Пагинация ограничивается общим бюджетом вызовов. Дубли удаляются по устойчивому идентификатору предложения и тарифу, без слияния разных условий. Остановка при has_more=true отмечается как неполный поиск.

Если подходящего нет, агент говорит «не нашёл среди проверенных вариантов» и указывает область поиска. Для предложения компромисса выполняется отдельный поиск с явным изменением ограничений. Обязательное условие пользователя не снимается автоматически.

## 9. Режим воспроизведения и имеющиеся данные

В проекте уже есть [архив Туту Москва — Ереван](exports/tutu-yerevan-2026-10-26/README.md): запросы, исходные ответы, инструкции, схемы, цены, выбранные тарифы и отзывы, полученные 26 октября.

ReplayAdapter:

- сопоставляет инструмент и нормализованные аргументы с сохранённым запросом;
- возвращает ответ с data_origin=recorded_fixture и исходным временем;
- на отсутствующий запрос возвращает fixture_missing, не придумывает результат;
- не формирует рабочие handoff-ссылки из записей, не открывает сохранённые ссылки оформления и не выполняет внешние изменяющие действия;
- позволяет управляемо воспроизводить изменение цены, таймаут и недоступность через отдельные явно синтетические записи.

Архив — хорошая основа проверки парсинга. Он не покрывает все направления, семейные поездки, поезда и произвольные даты. Нужные дополнительные сценарии создаются как подписанные synthetic fixtures или записываются отдельными разрешёнными запросами чтения.

Исторический контрольный итог: 35 218 ₽ за выбранный перелёт + 32 702 ₽ за семь ночей = 67 920 ₽. Сумма не включает трансферы, прочее питание, страховку и экскурсии. Проверка должна воспроизвести этот состав, не назвать его полной ценой любых расходов поездки.

Неизменённые исходники остаются в exports. Тестовые копии очищаются от чувствительных/временных ссылок и ненужных идентификаторов перед публикацией. Рабочие ссылки и значения токенов не переносятся в промпты и общие логи без необходимости.
