# Агент путешествий: спецификация реализации

Дата: 27 октября 2026. Статус: проект реализации, согласованный стек; код по этой спецификации ещё не создан.

Это описание самостоятельной агентской части продукта. Оно предназначено разработчику агента и разработчику будущего бэкенда. Здесь определены поведение, внутренние данные и граница подключения; HTTP-сервер и интерфейс сейчас не нужны.

## 1. Что зафиксировано

| Решение | Статус |
|---|---|
| Агентскую часть делает пользователь; бэкенд — другой участник | Подтверждено |
| Python + LangChain + LangGraph | Подтверждено |
| Использование skills внутри агента | Добавлено по уточнению пользователя 27 октября |
| Вызовы модели через Hugging Face | Подтверждено; модель и обслуживающий провайдер ещё не выбраны |
| FastAPI для будущего бэкенда | Подтверждено |
| Фронтенд, вероятно, React | Предварительно; агент от этого выбора не зависит |
| Туту MCP как источник предложений | Обсуждён и проверен; есть сохранённые ответы |
| Реальные цены и наличие — только из инструментов | Правило проектируемой реализации |
| Локальное имитированное оформление | Предлагаемый основной режим; реальная бронь поставщика в этот объём не входит |

Исходные требования и исследование: [CONTEXT.md](CONTEXT.md), [RESEARCH_COMPETITORS.md](RESEARCH_COMPETITORS.md). Это исторические документы от 26 октября: перечисленные там неизвестные стек и роли уже уточнены таблицей выше.

## 2. Результат работы

Нужен Python-пакет с асинхронным интерфейсом и консольным клиентом. Пользователь может начать с обычного сообщения, уточнить условия, получить конкретные варианты, собрать поездку, изменить её и завершить имитированное оформление.

Агент должен:

1. Извлекать условия поездки из свободного текста и помнить уже полученные ответы.
2. Задавать только вопросы, без которых нельзя выполнить следующий полезный шаг.
3. Предлагать направления, когда место ещё не выбрано.
4. Искать отели, перелёты и поезда; получать подробности выбранных тарифов.
5. Проверять обязательные условия, совместимость частей и состав стоимости.
6. Ранжировать варианты с учётом ситуации и накопленных предпочтений.
7. Объяснять причины выбора, компромиссы и неподтверждённые условия.
8. Перестраивать поездку при изменениях, сохраняя закреплённые пользователем части.
9. Отвечать на вопрос о поездке, не теряя незавершённый подбор.
10. Создавать однозначно обозначенный демонстрационный заказ после подтверждения.

Предлагаемые стартовые границы: русский диалог, расчёты в RUB, одна основная точка назначения, дорога туда/обратно и проживание. Направления не зашиваются под один показательный маршрут: поиск работает в пределах возможностей поставщика. Сложный маршрут из нескольких городов возвращает понятное ограничение возможностей.

Трансфер — отдельный компонент плана. Пока нет проверенного источника маршрутов, времени и тарифа трансфера, он остаётся незакрытым участком: нельзя придумывать цену или объявлять полную совместимость поездки. Синтетический трансфер допустим только в явно обозначенном тестовом сценарии. Подключение реального источника предусмотрено контрактом.

Сейчас не требуются FastAPI, React, авторизация веб-приложения, платёжная система, паспортные данные, распределённая инфраструктура или обучение собственной модели рекомендаций.

## 3. Устройство

Один агент с управляемым графом и специализированными функциями достаточен. Два сценария с доски — подбор и свободный вопрос — являются ветками одного состояния, а не обязательными отдельными агентами.

~~~mermaid
flowchart TD
    Input["Сообщение или действие пользователя"] --> Parse["Разбор намерения и изменений"]
    Parse --> Validate["Проверка запроса"]
    Validate -->|Не хватает важного| Ask["Уточнение"]
    Validate -->|Можно продолжать| Route["Выбор следующего шага"]
    Route --> Skills["Выбор и загрузка применимых skills"]
    Skills --> Search["Поиск через адаптер Туту"]
    Skills --> Question["Ответ по имеющимся фактам"]
    Search --> Normalize["Нормализация и проверка условий"]
    Normalize --> Rank["Ранжирование и сборка планов"]
    Rank --> Present["Варианты, причины, неизвестное"]
    Present -->|Выбор или изменение| Parse
    Present -->|Оформление| Refresh["Повторная проверка выбранного"]
    Refresh --> Confirm["Подтверждение конкретного плана"]
    Confirm --> Demo["Локальный демонстрационный заказ"]
~~~

LLM решает, что пользователь имеет в виду, какие сведения уточнить, какой разрешённый инструмент вызвать и как объяснить результат. Обычный Python-код отвечает за деньги, даты, ограничения, версии, разрешения на действия и запись состояния.

| Слой | Ответственность |
|---|---|
| AgentService | Публичный интерфейс, обработка одного сообщения, идентификаторы и повторы |
| LangGraph | Переходы между шагами, ограниченные циклы инструментов, остановка на вводе пользователя |
| SkillRegistry / SkillLoader | Каталог навыков, выборочная загрузка инструкций и материалов |
| Domain | Модели поездки, проверка условий, стоимость, ранжирование, сравнение версий |
| ModelGateway | Hugging Face, преобразование сообщений и вызовов функций, обработка ошибок модели |
| TravelToolsAdapter | Туту MCP или воспроизведение сохранённых ответов через единый контракт |
| Repositories | Поездки, версии планов, профиль, события, снимки предложений и демонстрационные заказы |
| CLI | Текстовый запуск агента и просмотр структурированного результата |

Нормализация и проверки входят в агентский пакет уже сейчас. Позже их можно вызывать из FastAPI вместе с агентом; отсутствие отдельного бэкенда не означает отсутствие обычной программной логики.

### Skills как часть целевой архитектуры

Использование skills — явное требование к агентской части. Навык хранит специализированную процедуру: когда применять её, какие данные получить, как выбрать следующий шаг и что считать результатом. В нашем продукте навыки работают внутри одного агента с общим состоянием поездки.

Формат: каталог навыка с SKILL.md; YAML-поля name и description описывают его назначение, тело содержит инструкции. Дополнительные references загружаются по необходимости. Это соответствует [формату Agent Skills](https://agentskills.io/specification).

Предлагаемый набор:

| Навык | Когда применяется | Результат |
|---|---|---|
| plan-trip | Новая поездка: нужно уточнить намерение, подобрать направление и найти первый набор предложений | Запрос поездки и проверяемые варианты |
| compare-offers | Уже есть кандидаты; требуется сравнить условия и цену предпочтений | Сравнение с доказательствами и компромиссами |
| replan-trip | Меняются условия существующего плана | Новая версия, сохранённые закрепления и diff |
| personalize-trip | Есть подходящие сохранённые предпочтения или пользователь явно корректирует профиль | Обоснованные признаки ранжирования либо проверяемое изменение профиля |
| rail-seat-groups | Нужно проверить конкретные места вместе, купе или полки | Подтверждённая группа мест либо причина неизвестности/несоответствия |
| finalize-trip | Пользователь выбрал состав и хочет перейти к оформлению | Подготовка подтверждения и разрешённого demo/handoff-действия |

Каталог name + description доступен модели заранее. После выбора навыка загрузчик передаёт его тело в контекст; дополнительные материалы читаются отдельно. Все навыки целиком в общий промпт не вставляются. Такой способ подключения описан в [руководстве интеграции Agent Skills](https://agentskills.io/client-implementation/adding-skills-support).

В нашей реализации SkillRegistry и SkillLoader входят в Python-пакет. Hugging Face исполняет модель; обнаружение и загрузку локальных навыков организует приложение. LangGraph выбирает маршрут и обеспечивает переходы, а skills дают инструкции для соответствующей задачи.

Правила реализации:

- Загружаются только поставляемые с приложением проверенные навыки из src/travel_agent/skills/. Пользовательские сообщения, отзывы и ответы MCP не могут добавлять туда исполняемые инструкции.
- Выбор учитывает смысл запроса и состояние, а не одно совпавшее слово. Для простого ответа допустим путь без навыка. Совместимые навыки можно подключать последовательно.
- Смена навыка сохраняет поездку, ограничения и выбор пользователя. Изменения применяются через существующие доменные проверки.
- Навык не расширяет разрешения инструментов и не отменяет подтверждение. Даже finalize-trip не может вызвать реальное бронирование в режиме demo.
- Формулы цены, проверка мест, версии и запись заказа остаются в Domain и сервисах. Инструкции навыка указывают, когда применять эти функции, и не заменяют их выполнение текстом.
- Для отладки сохраняются имя, версия/хеш загруженного содержимого и причина выбора; постоянный профиль пользователя не используется как хранилище активных skills.
- После сжатия контекста нужные инструкции восстанавливаются по зафиксированной версии. Недоступный или некорректный навык возвращает явную ошибку, а не обещание, что он применён.
- Общие правила продукта хранятся в одном месте; в skills остаётся специфика сценария. Произвольный запуск scripts или shell в этот объём не входит.

## 4. Поведение графа

Узлы: load_context → interpret → validate_request → route → select_skills/load_skills → search/details → normalize → validate_plan → rank → respond → persist. Ветки: clarify, answer_question, replan, prepare_confirmation, await_confirmation, create_demo_order.

Правила переходов:

- Уточнение заканчивает текущий вызов. Агент не ждёт ответа внутри бесконечного цикла.
- Для живого поиска нужны параметры соответствующего инструмента: маршрут/город, даты и состав пассажиров/гостей. Возраст ребёнка запрашивается, когда от него зависит тариф или размещение.
- Для вдохновения необязательно знать все поля. Можно предложить несколько направлений и спросить даты; конкретную доступность и цену до поиска не обещать.
- Необязательный бюджет не блокирует поиск, если остальные параметры известны. Для запроса «до 100 тысяч за всё» необходимо понять состав расходов и участников.
- Противоречащие явные обязательные условия требуют уточнения. Желательное условие можно ослабить в альтернативе, явно показав это.
- Пустая выдача, ошибка поставщика и остановка по лимиту — разные результаты.
- Свободный вопрос не сбрасывает поездку. Вопрос о тарифе ведёт к деталям предложения. Актуальные визовые, погодные и другие внешние факты без источника отмечаются как непроверенные.
- Если пользователь меняет условия во время ожидания подтверждения, старое действие отменяется; граф возвращается к разбору изменений.
- При исчерпании бюджета инструментов возвращаются полученные результаты и границы поиска; продолжение возможно следующим запросом.

Начальные технические пределы — настраиваемые гипотезы: 6 последовательных циклов LLM → tools за один ход, 20 внешних вызовов, параллелизм 3, дедлайн хода 90 секунд и запроса к инструменту 20 секунд. Не более двух повторов временного сбоя чтения в пределах общего дедлайна; параметры уточняются измерениями. Переходы графа ограничиваются отдельно, поскольку число узлов больше числа вызовов LLM.

В контекст модели передаются краткие нормализованные карточки и ссылки на доказательства. Полные JSON, все отзывы и все места поезда не добавляются на каждый ход. История может сжиматься, но структурированные обязательные условия, выбранные компоненты и подтверждения не заменяются пересказом.

## 5. Состояние и данные

Все внешние входы и ответы LLM валидируются Pydantic-моделями. LLM предлагает изменения, а код проверяет их и применяет. Неизвестное поле не получает удобное выдуманное значение.

### TripRequest

- origin, destination_candidates, selected_destination;
- departure_date, return_date, check_in, check_out, flexibility;
- party: adults, children с возрастами, infants, pets;
- budget: amount_minor, currency, party_scope, included_components;
- intent: отдых, работа, семья и другие явно указанные цели;
- constraints: идентификатор, поле, оператор, значение, hard/soft, источник;
- priorities: желаемые свойства с весами;
- assumptions: отдельно перечисленные рабочие предположения;
- unresolved_questions: только актуальные неизвестные.

Относительные даты вычисляются от переданного now и timezone. Если смысл «на следующие выходные» неоднозначен, агент показывает конкретные даты до поиска/выбора. Время транспорта хранится с часовым поясом; длительность считается по моментам времени, не вычитанием местных часов.

### OfferSnapshot

Минимальный состав:

- snapshot_id, provider, product_type, provider_refs;
- data_origin: live / recorded_fixture / synthetic;
- fetched_at, source_recorded_at, expires_at, freshness;
- query: маршрут, даты, участники и применённые фильтры;
- price: amount_minor, currency, basis, covered_party, covered_period, included, excluded, unknown_charges;
- conditions: багаж, питание, отмена, оплата, размещение и другие переданные условия;
- availability: reported_available / unavailable / unknown;
- evidence_refs: ссылки на вызов инструмента и конкретные поля ответа;
- raw_payload_ref, completeness и границы прочитанной выдачи.

Для live source_recorded_at может совпадать с fetched_at; для fixture дата записи источника не меняется при воспроизведении. Если поставщик не сообщил expires_at, это null. Внутреннее правило повторной проверки не является гарантированным сроком жизни тарифа.

Суммы RUB хранятся в копейках целым числом, входные дробные значения разбираются через Decimal. Неизвестные сборы не равны нулю. Для иной валюты нужен отдельный расчёт с источником и временем курса; до его появления суммы показываются раздельно.

### ConstraintCheck и PlanVersion

Для каждого условия: constraint_id, status = satisfied / violated / unknown, evidence_refs, explanation.

PlanVersion содержит plan_id, version, parent_version, request_revision, компоненты со snapshot_id, закрепления, результаты проверок, сумму известных расходов, неоценённые расходы, причины выбора и diff относительно предыдущей версии.

- Hard + violated: вариант не подходит, но может быть показан как подписанная альтернатива.
- Hard + unknown: вариант требует проверки, его нельзя выдавать за полностью подходящий.
- Все нужные подтверждения должны относиться к конкретному тарифу, датам и участникам.
- Отсутствие одного критичного компонента не скрывается общей суммой остальных.
- Рейтинг и расстояние до центра не доказывают тишину, расстояние до моря или время в пути.
- Совместимость проверяется по датам, часовым поясам, прибытию/отправлению, заселению и переездам. Неизвестное время трансфера оставляет соответствующую проверку unknown.

### AgentState

Хранит session_id, user_id, state_version, data_mode, checkout_mode, intent, запрос поездки, текущий plan_id/version, кандидатные планы, текущий вопрос, pending_action, ссылки на факты и результаты поиска, статус графа, active_skills (имя и версия/хеш) и счётчики текущего хода.

state_version — версия состояния диалога; plan.version меняется при изменении плана. Это разные счётчики. session_id обозначает одну поездку/диалог, user_id — профиль человека между поездками.

## 6. Персонализация и рекомендации

Нужны три раздельных слоя:

| Слой | Пример | Как используется |
|---|---|---|
| Текущая поездка | «С детьми, сейчас экономим, нужно одно купе» | Управляет условиями этого поиска |
| Явное постоянное предпочтение | «В командировках предпочитаю бизнес» | Применяется в соответствующем контексте |
| Гипотеза из поведения | Часто выбирает завтрак | Мягко влияет на порядок; может быть ошибочной |

Запись Preference: key, value, scope, source_type, source_event_ids, created_at, updated_at, evidence_count, confidence, status. Явное предпочтение не получает фиктивную статистическую вероятность. Confidence для гипотезы — внутренняя оценка с понятным правилом, а не калиброванная уверенность LLM.

Приоритет: явные условия текущей поездки → применимые постоянные предпочтения → гипотезы → общие начальные приоритеты. Противоречие двух обязательных пользовательских требований выясняется вопросом.

Поездка в Египет за 150 тысяч на две недели сама по себе не означает «бюджетный человек» или «всегда эконом». Нужны состав группы, включённые расходы, сезон и контекст. Событие сохраняется с известными полями; отсутствующее не достраивается.

Новый пользователь получает разнообразную стартовую подборку. Название «популярное» допустимо при наличии измеримой статистики и периода; без неё это «идеи для начала». Общие приоритеты не записываются в профиль как предпочтения человека.

Первое ранжирование реализуется кодом:

1. Проверить обязательные условия.
2. Отделить подходящие варианты от вариантов с неизвестными условиями и компромиссами.
3. Для сравнимых вариантов посчитать нормированные признаки: цена, длительность, отмена, питание, расположение, соответствие явным предпочтениям.
4. Применить прозрачные веса из запроса и профиля.
5. Добавить разнообразие результатов, чтобы не показать три почти одинаковых предложения.
6. Сформировать explanation_facts для LLM: фактические плюсы, минусы и неизвестное.

Отсутствующий признак не получает лучший балл. Нельзя компенсировать нарушение hard-условия высоким общим рейтингом.

События: shown, viewed, saved, selected, rejected с причиной, demo_order_created. Демонстрационный заказ не записывается как реальная покупка. Невыбранный вариант не считается отказом. Пользователь может исправить или удалить предпочтение.

Embeddings, векторная база и обучаемая рекомендательная модель сейчас необязательны. Они могут улучшить смысловой подбор после появления данных; числовые ограничения и проверка доступности остаются обычным кодом.

## 7. Три отличительные возможности

### Цена предпочтения

Агент сравнивает реально найденные альтернативы: например, с завтраком и без, прямой перелёт и пересадку, фиксированные даты и соседние. Разницу вычисляет код.

Сравнение содержит, какие условия отличаются. Если вместе с завтраком поменялись номер и отмена, разницу нельзя целиком назвать ценой завтрака. Формулировка — «этот набор условий дешевле на …».

### Пересборка с сохранением выбора

Пользователь может закрепить отель как объект, конкретный рейс, даты или бюджет. Тип закрепления указан явно: сохранить отель не означает сохранить старый тариф на новые даты.

Изменение создаёт новую версию плана: что осталось, что заменилось, почему, разница известных расходов и времени. Если закреплённое несовместимо с новым запросом, агент показывает конфликт и предлагает выбор.

Откат восстанавливает намерения и состав предыдущего плана, после чего перепроверяет меняющиеся предложения. Он не восстанавливает утраченную доступность или цену.

### Семья едет вместе

«Рядом» уточняется, если это существенно: одно купе, соседние сиденья, нужное количество нижних полок. Для железной дороги проверяются конкретные свободные места, вагон, секция/купе, категория и ограничения тарифа.

Четыре свободных места в поезде не означают четыре места в одном купе. Противоречивые данные о вместимости и категории не принимаются за подтверждение. Возможности инструмента подробно описаны в [AGENT_TOOLS.md](AGENT_TOOLS.md).

## 8. Интерфейс для консоли и будущего бэкенда

Это проект интерфейса; функций пока нет.

~~~python
async def run_turn(
    request: TurnInput,
    *,
    on_event: EventSink | None = None,
) -> TurnResult: ...

async def get_session(user_id: str, session_id: str) -> SessionSnapshot: ...
~~~

TurnInput:

- schema_version = 1;
- request_id — ключ повтора пользовательского хода;
- user_id, session_id;
- expected_state_version — 0 для новой сессии;
- input — одно из message, select_option, confirm_action, reject_action, undo, update_preference;
- payload — текст или типизированные аргументы соответствующего действия;
- now и timezone — задаются приложением, не LLM.

Структурированный выбор ссылается на option_id и версию выдачи. Текстовое «второй» разрешается только при однозначной связи с последней актуальной выдачей.

TurnResult:

- request_id, session_id, state_version;
- status: needs_input / options_ready / plan_ready / needs_confirmation / completed_demo / handoff_ready / in_progress / partial / error;
- message;
- questions, options, current_plan, plan_diff;
- pending_action, demo_order, handoff;
- handoff: необязательный HandoffResult с provider, URL, plan_id/version, временем формирования и явным признаком отсутствия подтверждённой покупки;
- evidence, warnings, search_coverage;
- error: code, retryable, понятное explanation при ошибке.

Подтверждение содержит action_id, plan_id, plan_version и payload_hash. Они сверяются с сохранённым pending_action. Текстовое «да» принимается только для единственного актуального явно заданного вопроса.

События on_event: stage_changed, skill_loaded, tool_started, tool_finished, options_updated, confirmation_required, completed. Каждое имеет event_id, run_id, sequence, timestamp и типизированный payload. Пользовательский поток не содержит секреты, полные трассировки и скрытые рассуждения модели.

Будущий FastAPI вызывает AgentService, передаёт проверенный user_id и отдаёт результат/поток событий. Он отвечает за HTTP, авторизацию, ограничения доступа и доставку событий. Агент не импортирует FastAPI или React.

## 9. Хранение, повтор и восстановление

Для самостоятельного запуска: локальный SQLite для доменных данных и файловый SQLite-checkpointer LangGraph. Постоянный профиль хранится отдельно от состояния конкретного графа. Это соответствует разделению [checkpointer и store в LangGraph](https://docs.langchain.com/oss/python/langgraph/persistence).

TripRepository — источник истины для запросов, версий планов и pending_action. Checkpoint хранит ход исполнения и ссылки/рабочую копию; после возобновления версии сверяются с репозиторием. Несогласованная рабочая копия не перезаписывает более новое состояние.

- В пределах процесса ходы одной сессии выполняются последовательно; разные сессии могут работать параллельно.
- Запись состояния проверяет expected_state_version. При конфликте — state_conflict, без потери чужих изменений.
- Сначала проверяется ключ (user_id, session_id, request_id) и отпечаток входа. Совпадающий завершённый повтор возвращает сохранённый результат; выполняющийся — in_progress. Тот же ключ с другим входом даёт конфликт. Только для нового запроса проверяется expected_state_version: успешный повтор не должен отклоняться из-за версии, изменённой им самим.
- Демонстрационный заказ и отметка выполнения action_id записываются одной транзакцией с уникальным ключом.
- Checkpoint не заменяет идемпотентность действий: восстановление после падения может повторно войти в узел.
- Перед ответом о завершении проверяется фактическая запись заказа.
- При отмене или дедлайне сохраняется согласованное состояние, а не половина нового плана.

В LangGraph ожидание подтверждения можно оформить через interrupt и продолжение Command(resume=...) с тем же thread_id. Возобновляемый узел запускается заново, поэтому создание заказа выполняется после проверки подтверждения в отдельном защищённом узле. [Правила interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts).

## 10. Оформление

Две настройки: data_mode = live / replay и checkout_mode = demo / handoff / disabled. Сочетание replay + handoff запрещено. Режимы сохраняются при создании сессии; для их смены создаётся новая сессия, без переноса действительности прежних предложений и подтверждений. Перед handoff код дополнительно проверяет data_origin каждого выбранного снимка: только live. Режима реального автоматического бронирования в этой реализации нет.

Основной сценарий — live + demo:

1. Пользователь выбирает конкретные компоненты.
2. Агент повторно проверяет меняющиеся предложения подходящим способом; простое форматирование сохранённой карточки не считается перепроверкой.
3. Показывает состав, актуальные известные суммы, условия, неоценённые расходы и явную пометку имитации.
4. Создаёт pending_action с версией и отпечатком содержимого.
5. Получает подтверждение именно этого действия.
6. Записывает DemoOrder: local_id, action_id, plan_id/version, mode=demo, status=simulated_confirmed, created_at, подтверждённый состав.
7. Возвращает: «Демонстрационный заказ создан. Реальные билеты и номера не забронированы».

Существенное изменение цены, тарифа, участников, условий или состава после подтверждения аннулирует действие. Критичное неизвестное по оформляемому компоненту блокирует статус готовности; пользователь может явно изменить требование или состав плана.

replay + demo проверяет механику на исторических/синтетических данных и всегда обозначается как тест. handoff формирует разрешённую ссылку поставщика и сообщает о переходе; ни ссылка, ни её выдача не означают завершение покупки. Эти операции имеют разные статусы.

## 11. Надёжность и наблюдаемость

- Внешний текст из MCP, описаний отелей и отзывов — данные, не инструкции, способные изменить правила агента.
- Разрешённые инструменты и аргументы проверяются кодом. Модель не получает произвольный доступ к сети, файлам и shell.
- Сбой live-источника не переключает агента на архив незаметно.
- Ошибки транспорта, лимит, пустой результат, ошибка схемы и неподдерживаемая возможность различаются.
- Неизвестный инструмент, некорректные аргументы или неверный JSON модели возвращаются в ограниченный цикл исправления, а не исполняются.
- Никакого автоматического вызова register_checkout_passengers.
- В логи пишутся тип операции, длительность, результат, число предложений и идентификаторы доказательств; токены, секреты и чувствительные ссылки скрываются.
- Профили и поездки разных user_id не смешиваются. Удаление профиля включает производные гипотезы и связанные записи памяти.
- Метрики: время до первого полезного ответа, число уточнений, завершённые сценарии, ошибки проверок, количество/стоимость LLM-вызовов при наличии тарифа и доля подтверждённых условий. Измерения live и replay разделяются.
