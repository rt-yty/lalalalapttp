# Обязательный вход и сохранение прежних поездок

Приложение поддерживает регистрацию и вход по email и паролю. Аккаунты,
сессии входа и ограничения частоты запросов сохраняются в Postgres; SQLite
используется в автономных проверках. Вход с другого устройства открывает
те же поездки и явно сохранённые предпочтения.

Без регистрации и входа приложение не выполняет запросы агента, поиск,
расшифровку голоса, создание и продолжение поездок, чтение истории, результатов
или предпочтений. Сервер возвращает HTTP 401 до чтения тела запроса и запуска
работы. Эта проверка действует для всех бизнес-маршрутов `/api/*`, включая
неизвестные и прежние адреса; она не зависит от состояния интерфейса.
Публичны только интерфейс и его ресурсы, `/api/bootstrap`, `/api/health` и
маршруты регистрации, входа, выхода и проверки аккаунта `/api/auth/*`.
Swagger/OpenAPI не опубликованы.

Локальный операторский скрипт настройки поиска сохраняет ключи в `.env` и
самостоятельно проверяет подключение поставщика. Он не обходит вход в аккаунт:
если работающий сервер требует авторизацию, скрипт не отправляет ключи в его
анонимный API и предлагает перезапустить приложение для чтения `.env`.

Email пока служит логином: `email_verified` всегда `false`. Письма не
отправляются. Подтверждение адреса и восстановление забытого пароля требуют
отдельного почтового подключения и сейчас не представлены как работающие
функции. Приложение не утверждает, что пользователь владеет указанным адресом.

## HTTP-контракт

Сначала клиент вызывает `GET /api/bootstrap`. Ответ содержит `user` либо `null`
и `csrf_token`, а также `auth_required: true`; браузер сохраняет HttpOnly cookie.
При `user: null` интерфейс показывает вход и регистрацию, не запрашивая поездки
или профиль. Все изменяющие запросы,
включая вход и выход, передают `X-Travel-Token` и выполняются с того же origin.

| Запрос | Вход | Результат |
|---|---|---|
| `POST /api/auth/signup` | `{email,password,name?}` | HTTP 201, аккаунт и сессия входа |
| `POST /api/auth/login` | `{email,password}` | HTTP 200, новая сессия входа |
| `GET /api/auth/me` | — | `{user,csrf_token}` |
| `POST /api/auth/logout` | `{}` | Текущая сессия отозвана, доступ к приложению закрыт до входа |

`user` содержит `id`, `email`, `name`, `email_verified`. Пароль — от 12 до
128 символов; он не обрезается и не нормализуется. Email проверяется библиотекой
email-validator и приводится к единому регистру. Имя необязательно, до 80 символов.
Валидационные ответы не возвращают введённые пароли, тела запросов или лишние поля.

После signup/login/logout клиент заменяет свой CSRF-токен значением из ответа.
После входа он загружает поездку, историю и профиль заново, после выхода очищает
их из интерфейса и возвращается к форме входа. HTTP 401 на бизнес-запросе требует
обновить bootstrap и закрыть рабочий интерфейс, если аккаунт отсутствует.
Signup/login также возвращают:

```json
{
  "guest_migration": {
    "moved_sessions": 2,
    "session_id_map": {"old-id": "new-id"},
    "profile_preferences_not_imported": 0
  }
}
```

Новые гостевые поездки не создаются. Уже сохранённые данные прежней версии не
удаляются и доступны для переноса после успешного входа или регистрации по
сохранившейся подписанной cookie этого браузера. До входа эта cookie разрешает
только CSRF-проверку регистрации и входа, но не доступ к данным или поиску.
Обычно идентификатор прежней поездки остаётся прежним. Если в аккаунте уже есть поездка
с таким идентификатором, гостевая получает новый; интерфейс применяет
`session_id_map` к текущей поездке. Нельзя начинать перенос, пока для гостя
выполняется запрос: сервер возвращает HTTP 409 и не создаёт частичный аккаунт.
Сохранённый запрос, время и квитанция переносятся вместе; точный повтор не
дублирует выполненное действие.

При переносе сохраняется город аккаунта, если он уже задан. Гостевые пожелания
дополняют существующие до лимита десяти, с приоритетом аккаунта. Число пожеланий,
не попавших в активный профиль, возвращается отдельно. Исходный гостевой профиль
остаётся во внутреннем архиве; публичного доступа по прежней cookie больше нет.
Параметры уже созданных поездок не переписываются.

## Защита

Пароли хешируются `scrypt` с отдельной случайной солью: N=131072, r=8, p=1.
Хеширование выполняется вне основного цикла обработки запросов: одновременно
не более двух вычислений, всего не более восьми ожидающих запросов авторизации.
Отмена HTTP-запроса не освобождает вычислительный слот до завершения scrypt.

Cookie аккаунта содержит случайный 256-битный токен; в базе хранится только его
SHA-256. Сессия действует 30 дней. Вход обновляет токен, выход удаляет его из базы;
повтор старой cookie не восстанавливает доступ. Cookie имеют HttpOnly,
SameSite=Lax и Path=/; при HTTPS автоматически добавляется Secure и префикс
`__Host-`, запрещающий подмену аккаунтной cookie через соседний поддомен. Для внешнего
развёртывания используйте HTTPS и `COOKIE_SECURE=true`. HTTP допустим для
локального запуска на 127.0.0.1.

Ограничения входа сохраняются при перезапуске: до 10 попыток на email и до 30
на IP за 15 минут, регистрация дополнительно до 10 попыток на IP в час.
В таблице лимитов находятся HMAC-ключи, а не открытые IP/email. При превышении
возвращается HTTP 429 с `Retry-After`. Неверный пароль и неизвестный email
получают одинаковый ответ и одинаковую процедуру scrypt-проверки.

Прежняя гостевая cookie после переноса отзывается. Она не превращается в
способ входа в аккаунт. Выход создаёт только анонимный контекст для следующего
входа; аккаунтные поездки не становятся общими для следующего пользователя
этого браузера. Подмена, истечение срока или повтор отозванной cookie аккаунта
возвращают HTTP 401 для бизнес-запросов и не включают гостевой режим.

Основание параметров: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
и [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
